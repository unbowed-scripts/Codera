# PythonTech Android: план разработки учебной среды

Дата: 13 октября 2026 года.
Статус: план следующих работ, а не описание готовых возможностей.
База: настольный выпуск PythonTech 0.7.0 и отдельный Android-прототип 0.7.0-alpha.1.

**Цель — проходить Python на телефоне: читать урок, писать и запускать код, получать обратную связь и сохранять проект. Компьютерная версия продолжает работать привычным способом.**

## 1. Что уже есть

- Настольное приложение на Python и PySide6; интерфейс на Qt Quick/QML.
- 54 урока Python Core и 42 урока Web, задания, подсказки и мини-проекты.
- Сжатый каталог `courses.zip`, загрузка отдельных уроков и кэш до 12 уроков в готовых сборках 0.7.0.
- Проверка текстовых ответов и сохранение отметок через `QSettings`.
- Android-сборка ARM64 на Python 3.11, PySide6 6.8.2.1 и python-for-android. Текущий сценарий сборки находится в `tools/build_android.py`.
- Существующий APK alpha.1 не содержит последующих изменений настольной 0.7.0.

Сейчас приложение не выполняет код ученика. Отметки практики и проектов пользователь ставит самостоятельно. Черновики ответов не переживают закрытие приложения. ИИ-помощник не читает файлы автоматически и не запускает код.

Сведения о текущей сборке: [ANDROID.md](ANDROID.md). Устройство учебного архива: [STORAGE.md](STORAGE.md).

## 2. Основные решения

1. Сохранить один репозиторий и разделить общую учебную логику и платформенные приложения.
2. Не менять внешний вид и поведение Windows/Linux ради Android. Изменения общей части проверять на обеих настольных системах.
3. Сначала довести учебный путь на Python. Другие языки добавлять после проверки этой основы.
4. Проверить запуск кода на настоящем телефоне до переноса всех экранов и массового перевода уроков.
5. Оставить обучение офлайн. Интернет нужен для загрузки дополнительных компонентов и задач, явно использующих внешние сервисы.
6. Не обещать поддержку произвольного пакета из PyPI. Показывать только проверенные возможности выбранной среды.
7. Встроенный Python — основной сценарий. Termux — возможная дополнительная интеграция, не обязательная зависимость первого прототипа.

Названия направлений для документации: **PythonTech Desktop** и **PythonTech Android**. Это обозначения платформ, а не требование переименовать приложение или разделить учебные материалы.

## 3. Как разделить проект

Предлагаемая структура; этих папок пока нет, переносить файлы нужно постепенно:

```text
shared/
  content/             # Модели, каталог, идентификаторы и схема материалов
  learning/            # Правила проверки и расчёт учебного прогресса
  contracts/           # Интерфейсы хранилища и среды выполнения
apps/
  desktop/             # Точка запуска и интерфейс компьютера
  android/             # Точка запуска и мобильные экраны
runtimes/
  android_python/      # Отдельная среда выполнения ученического кода
packaging/
  desktop/             # Windows и Linux
  android/             # APK, манифест и нативные зависимости
content_sources/       # Общие исходники курсов и переводы
```

Сначала выделить функции без Qt из `backend.py`: проверку ответов, расчёт прогресса и навигационные данные. `Backend(QObject)` оставить адаптером настольного интерфейса. Не делать массовый перенос файлов первым изменением.

Сохранить стабильные ключи уроков (`start/1` и другие), разделов и настроек. При перемещении модулей временно оставить совместимые импорты. `main.py` и существующие команды запуска должны работать до отдельного согласованного перехода.

Не менять расположение настольного `QSettings`, название организации и ключи прогресса. Android получает свой адаптер хранения. Общий формат не означает автоматическую синхронизацию устройств: перенос прогресса — отдельная функция.

## 4. Выбор мобильной технологии

Не переписывать интерфейс заранее. Первый прототип проверить на текущем Qt/QML с небольшим Android-мостом для запуска отдельного процесса и работы с жизненным циклом приложения.

Перед окончательным выбором подтвердить:

- корректную работу экранной клавиатуры, выделения, вставки и русского ввода;
- запуск и остановку Python отдельно от UI;
- восстановление после поворота, сворачивания и завершения процесса Android;
- совместимость нативных библиотек и разумный размер APK;
- передачу файлов проекта и вывода между процессами.

Если Qt-вариант не обеспечивает эти условия, подготовить сравнение с нативным Kotlin/Compose. Не переносить всю компьютерную часть на новый стек. Новая Android-оболочка может читать тот же архив курса; способ повторного использования учебной логики нужно доказать прототипом.

Python на Android встраивается в приложение и имеет платформенные ограничения. Использовать документацию CPython как основу проверки совместимости, а не считать Android обычным настольным Python: [Python on Android](https://docs.python.org/3.14/using/android.html).

## 5. Первый рабочий прототип

**Объём: один раздел «Начало», один проект с `main.py`, запуск Python без дополнительных пакетов.**

Путь ученика:

1. Открыть урок и прочитать задание.
2. Перейти в редактор с исходным примером или пустым файлом.
3. Написать программу и нажать «Запустить».
4. При `input()` ввести ответ в консоли.
5. Увидеть вывод либо ошибку с номером строки.
6. Исправить программу, повторить запуск и сохранить результат.
7. Закрыть приложение, открыть снова и продолжить с сохранённого кода.

Не включать в первый прототип установку пакетов, несколько языков, облачную синхронизацию и универсальный терминал.

Критерии приёмки:

- `print()`, арифметика, строки, циклы и `input()` работают без интернета.
- Неверный код показывает `SyntaxError` и строку ошибки, а не закрывает приложение.
- Бесконечный цикл останавливается кнопкой и по лимиту времени; следующий запуск работает.
- Очень большой вывод ограничивается и не блокирует интерфейс.
- Код восстанавливается после закрытия и повторного запуска приложения.
- Поворот экрана и появление клавиатуры не теряют текст.
- Сбой процесса выполнения не изменяет прогресс и настройки приложения.

## 6. Мобильный редактор и навигация

Предусмотреть три понятных экрана или вкладки: «Урок», «Код», «Результат». На телефоне не пытаться одновременно показывать всю настольную компоновку.

Редактору нужны подсветка, номера строк, автоотступ, отмена и повтор действия, поиск, копирование и вставка. Над клавиатурой — кнопки отступа, скобок, кавычек, двоеточия и знака равенства. Панель не должна перекрывать текущую строку.

Для проекта показать список файлов, создание и переименование. Подтверждать удаление пользовательского файла. Отличать сохранённый пример урока от редактируемой копии ученика.

Обязательные состояния: выполнение, ожидание ввода, остановка, успешное завершение и ошибка. Не сообщать «Сохранено» до подтверждения записи. Для несохранённого текста дать понятное действие при ошибке диска.

Проверить обычный телефон, узкую ширину, альбомную ориентацию, планшет, системное увеличение шрифта и внешнюю клавиатуру. Числа ширины в Qt и Android dp не считать автоматически одинаковыми единицами.

## 7. Запуск кода и граница доступа

Не выполнять ученический код через `exec()` в процессе интерфейса, ИИ-помощника или хранилища прогресса. Поток Python и замена `__builtins__` не являются изоляцией.

Предлагаемый контракт среды выполнения:

- `start`: идентификатор запуска, версия среды, файлы проекта, точка входа и лимиты;
- `stdin`: порция введённого текста или конец ввода;
- `stop`: остановка конкретного запуска;
- события: `started`, `stdout`, `stderr`, `waiting_input`, `finished`, `failed`;
- каждое событие содержит идентификатор запуска, чтобы старый вывод не попадал в новую консоль.

Сначала исследовать Android Service с `isolatedProcess` и встроенным CPython. Такой сервис имеет отдельные ограничения доступа; загрузку интерпретатора, файлов и пакетов нужно проверить на устройстве. Обычный сервис в другом процессе с тем же UID не обеспечивает изоляцию данных приложения. См. [Android: service / isolatedProcess](https://developer.android.com/guide/topics/manifest/service-element#isolated).

Передавать только файлы выбранного проекта через контролируемый канал. Не передавать ключи ИИ, настройки или базу прогресса. Проверить попытки выхода за каталог проекта, чтения закрытых данных и запуска дополнительных процессов.

Лимиты времени и объёма вывода обязательны. Механизм контроля памяти и принудительной остановки подтвердить экспериментом; не обещать жёсткую квоту памяти без измерений. Описать поведение при сворачивании и закрытии приложения. Первый вариант может останавливать задачу при уходе с экрана с понятным уведомлением.

Режимы с сетевым доступом и локальным Web-сервером проектировать отдельно: они могут потребовать другой границы доступа. Нельзя одновременно обещать полностью бесправный процесс и свободную работу любых сетевых библиотек без проверки архитектуры.

## 8. Проекты, прогресс и размер данных

- Материалы курса хранить один раз в сжатом архиве.
- Исходники ученика хранить как файлы проектов. Метаданные, привязки к урокам и состояние редактора — отдельно.
- Сохранять последний черновик каждого файла атомарно, с ограниченной частотой записи. Проверить сбой записи и завершение процесса во время сохранения.
- Не накапливать каждое нажатие клавиши и полный вывод всех запусков. Историю версий, если она появится, ограничить по количеству и объёму.
- Для SQLite-метаданных предусмотреть схему, миграции и резервную копию перед несовместимым изменением. Не переносить настольный прогресс в SQLite только ради единого названия хранилища.
- Экспортировать проект через системный выбор файла; импортировать с проверкой путей и размеров. Архив с `../` или абсолютными путями не должен писать вне проекта.
- Показывать отдельно размер курсов, сред выполнения, пакетов, проектов и удаляемого кэша.

Общий пакет использовать повторно только при совместимых версиях и ABI. Для проектов хранить список закреплённых зависимостей. Не удалять среду или пакет, который нужен сохранённому проекту, без объяснения последствий.

Пакеты и интерпретаторы могут занимать значительно больше места, чем уроки. Цель — предсказуемое использование памяти и диска, а не обещание нулевого размера.

## 9. Установка пакетов

Добавлять после работоспособного запуска стандартного Python.

1. Составить список библиотек, реально нужных заданиям курса.
2. Для каждой проверить лицензию, Python-версию, Android API, ABI и работу в выбранной среде.
3. Разделить чистые Python-пакеты и пакеты с нативными библиотеками. Для последних нужны совместимые Android-сборки; python-for-android использует специальные рецепты для части таких зависимостей: [документация](https://python-for-android.readthedocs.io/en/develop/).
4. Создать каталог проверенных версий с размерами, зависимостями и контрольными суммами. Проверять подлинность каталога, а не доверять одному хэшу из того же непроверенного источника.
5. Перед загрузкой показывать необходимое место, включая временную распаковку. Поддержать отмену, обрыв связи и повторную загрузку без повреждения установленной версии.
6. Устанавливать во временный каталог и активировать только после проверки. Предыдущая рабочая версия должна оставаться доступной при сбое.
7. Проверить запуск установленного пакета без интернета и понятную ошибку при отсутствии зависимости.

Не запускать произвольные установочные скрипты пакетов в процессе приложения. Установка через произвольный `pip install` не входит в первую поставку. Для распространения через Google Play отдельно проверить действующие правила загрузки исполняемого кода; выбор канала распространения сделать до реализации менеджера нативных компонентов.

## 11. Проверка практики

Сохранить различие между текстовым вопросом, запуском программы и автоматической проверкой задания.

Для задач с проверяемым результатом добавить отдельные данные: начальные файлы, входные примеры, ожидаемый результат, лимиты и требования к среде. Не смешивать их с текстом теории. Сохранить существующие ключи уроков и правильные ответы.

Отчёт проверки должен показывать, что проверено и где результат отличается. Одна успешная попытка запуска не означает прохождение задания. Открытые проекты, читаемость кода и объяснение решения могут по-прежнему требовать самостоятельной проверки.

Локальные тесты доступны владельцу устройства: это учебная обратная связь, не защищённый экзамен. ИИ-помощник остаётся отдельной подсказкой; не приписывать ему доступ к проекту и результатам без явно реализованной передачи контекста.

## 12. Переводы и другие языки

Сейчас подготовить стабильные ключи интерфейсных строк и формат локализованных полей материалов. Переводить законченные разделы после проверки исходного текста и кода. Не создавать независимые копии курсов для Android и компьютера.

Смена языка не должна сбрасывать прогресс. Примеры, задания и ожидаемые ответы переводить согласованно: строка, которую печатает пример, должна совпадать с проверкой. Для отсутствующего перевода использовать обозначенный исходный язык.

После полноценного Python оценить HTML/CSS/JavaScript с предпросмотром. Затем выбирать следующий язык по потребностям курса и результатам отдельного прототипа среды выполнения. Карточка языка в каталоге не означает поддержку его запуска.

Интерфейс среды выполнения должен позволять подключать разные реализации. Не скачивать все компиляторы заранее. Termux рассматривать как дополнительный режим после проверки интеграции, разрешений, возврата результата и установки пользователем: [официальный сайт](https://termux.dev/).

- Юнит-тесты общей логики и отдельные регрессионные проверки Windows/Linux.
- Реальное ARM64-устройство на минимально поддерживаемой версии Android и на актуальной версии; записать модели и версии в отчёт.
