# Инструкции для ИИ: PythonTech

Помогай читателю понять суть и применить её на практике. Эти правила относятся к урокам, заданиям, подсказкам, интерфейсу, документации и ответам о проекте.

## Стиль объяснений

- Начинай с главной мысли или нужного действия. Убирай вступления, повторы и детали, которые не помогают решить задачу.
- Пиши простыми словами и короткими предложениями. Сохраняй связность: текст не должен выглядеть как набор обрывков.
- Учитывай знания читателя. Для новичка объясняй термин при первом употреблении. Одно понятие называй одинаково во всём тексте.
- Один абзац — одна мысль. Сложную тему раскрывай последовательно: что это, как работает, какие есть ограничения.
- Добавляй пример только тогда, когда он помогает понять правило. Пример должен работать и соответствовать объяснению.
- Выбирай нужную глубину. На простой вопрос достаточно короткого ответа. Для сложного сохрани необходимые шаги и пояснения.
- Не сокращай текст ценой точности. Сохраняй условия, исключения, ограничения и различия между похожими понятиями.
- Пиши дружелюбно и уважительно. Избегай канцелярита, роботизированного тона, искусственной похвалы и обещаний, что всё «легко».
- Для действий используй глаголы: «Сохрани файл», «Запусти пример», «Проверь результат».
- Нумеруй последовательные шаги. Независимые правила и критерии оформляй отдельными пунктами.

## Как редактировать текст с помощью ИИ

1. Определи аудиторию, задачу читателя и формат: урок, подсказка, сообщение или документ.
2. Прочитай исходный текст и связанный код. Уточни факты по проекту и официальной документации.
3. Сначала исправь порядок мыслей, затем формулировки и оформление. Большой материал обрабатывай по темам.
4. Убери повторы и необязательные детали. Проверь, что краткая версия сохраняет смысл и ограничения.
5. Сверь команды, пути, числа и примеры с исходниками. Результат ИИ — черновик, который нужно проверить.
6. Выполни подходящие проверки. В отчёте укажи, что изменено, что проверено и что осталось непроверенным.

Не выдумывай инструменты, возможности приложения, результаты тестов и сведения из недоступных источников. Если информации не хватает, обозначь это прямо.

## Оформление уроков

Перед правкой реши, как подать тему. Не собирай теорию в один длинный абзац.

- Начинай с короткой **главной мысли**. Жирным выделяй её, а не всё объяснение.
- Разделяй основную мысль, правила, ограничения и пояснение примера.
- Теория поддерживает HTML: `<p>`, `<b>`, `<ul>`, `<li>`, `<code>`. Символы кода `<`, `>` и `&` экранируй как `&lt;`, `&gt;` и `&amp;`.
- В остальных учебных полях используй обычный текст и переносы строк. Не вставляй разметку, которую компонент не отображает.
- Самостоятельную работу разбивай на шаги. Для каждого результата указывай проверяемые критерии.
- Сохраняй рабочие примеры, правильные ответы, ключи уроков и совместимость сохранённого прогресса.
- Не меняй код ради стилистической правки. Если обнаружена ошибка в примере, исправляй её вместе с объяснением и проверками.
- После правки проверь экран на обычной и узкой ширине: переносы, выделения, обрезание и отсутствие видимых HTML-тегов.

## Тексты интерфейса

Используй короткие названия действий. Пиши «урок» для учебной страницы, «раздел» для группы уроков, «курс» для направления обучения.

Сообщение об ошибке должно объяснять, что произошло и что сделать дальше. Не обещай сохранение или выполнение действия, пока оно не подтверждено.

Различай автоматическую проверку ответов и самостоятельную проверку кода. Приложение не запускает код ученика. Отметки практики и проектов выставляет сам пользователь.

**Если задача касается текста, сохраняй дизайн:** цвета, шрифты, размеры, отступы и расположение элементов. Не сокращай важное пояснение только ради размещения в одну строку.

## Устройство проекта

PythonTech — настольное учебное приложение на Python и PySide6. Qt Quick/QML отвечает за интерфейс. Flask нужен для Web-примеров, но не для самого приложения.

| Файл или папка | Назначение |
| --- | --- |
| `main.py` | Запуск приложения и загрузка QML |
| `backend.py` | Навигация, проверка ответов, прогресс и данные экранов |
| `curriculum.py` | Структура курсов, первые три урока и сборка учебных данных |
| `core_content.py` | Остальные уроки Core и вводная практика |
| `web_content.py` | Базовые уроки Web и сборка всего Web-курса |
| `web_extended_content.py` | Связанные данные, пользователи, интеграции и запуск |
| `section_content.py` | Мини-проекты Core и итоговые вопросы |
| `web_projects.py` | Мини-проекты Web |
| `practice_hints.py` | Примеры кода для подсказок Core |
| `language_catalog.py` | Каталог языков и планы будущих курсов |
| `ai_tutor.py` | Запросы к ИИ, правила ответов и состояние подключения |
| `qml/` | Экраны, компоненты и тексты интерфейса |
| `themes.py` | Цвета и данные тем |
| `examples/` | Полные учебные проекты с проверками |
| `tests/` | Автоматические проверки приложения и учебных примеров |
| `tools/` | Скриншоты, проверка размещения и вспомогательные команды |
| `docs/` | Руководства по обучению, проектам и дизайну |
| `packaging/` | Подготовка сборок и сведения о выпуске |

Перед работой проверяй актуальное содержимое файлов. Эта карта помогает найти нужное место, но не заменяет чтение кода.

## Инструменты и порядок работы

| Задача | Инструмент | Как использовать |
| --- | --- | --- |
| Найти текст или файл | `rg`, `rg --files` | Если `rg` недоступен, используй `find`, `grep` или Python |
| Посмотреть изменения | Git | Начни с `git status --short`, проверяй итог через `git diff` |
| Изменить текст | Редактор или точечный патч | Правь исходное поле; избегай глобальных замен в коде и ответах |
| Проверить факты | Браузер и официальная документация | Открывай источник по конкретному вопросу, сохраняй полезные ссылки |
| Запустить приложение и проверки | Python из `.venv` | Используй окружение проекта, не подменяй системные пакеты |
| Проверить поведение | `unittest` | Выбирай проверки по затронутым файлам; при общей правке запускай весь набор |
| Проверить отображение | Qt, скрипты из `tools/`, просмотр PNG | Сочетай автоматические проверки с просмотром обычной и узкой версии |

Перед правками прочитай `AGENTS.md` и относящиеся к задаче документы. Не затирай чужие изменения. После правок проверь diff: стилистическая замена не должна менять идентификаторы, программные выражения и ожидаемые ответы.

### Команды из корня проекта

Установка зависимостей приложения и запуск:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python main.py
```

Для выполнения Web-примеров и их тестов:

```bash
.venv/bin/python -m pip install -r examples/web_notes/requirements.txt
```

Общая проверка без видимого окна:

```bash
QT_QPA_PLATFORM=offscreen QT_QUICK_BACKEND=software .venv/bin/python -m unittest discover -s tests -v
```

Проверка экранов и навигации:

```bash
.venv/bin/python tools/check_mobile_layout.py
.venv/bin/python tools/check_web_layout.py
```

Первый скрипт сохраняет изображения в `build/mobile-preview/`, второй — в `build/web-preview/`. Для изменённых экранов, которых нет в этих сценариях, выполни отдельную проверку. Просмотри изображения: успешный тест сам по себе не подтверждает удобство чтения.

На Windows используй `.venv\Scripts\python.exe` вместо `.venv/bin/python`. Переменные окружения задавай средствами своей оболочки.

## Встроенный ИИ-помощник

Правила ответов находятся в `SYSTEM_PROMPT` файла `ai_tutor.py`. Применяй к ним стиль из этого документа.

Помощник получает контекст выбранного задания, текущий ответ, вставленный код и вопрос. Он не читает файлы автоматически, не запускает код и не меняет прогресс. Не приписывай ему такие возможности в интерфейсе.

Давай следующий полезный шаг вместо полного решения теста. Пример кода нужен только при пользе для объяснения. В ответе помощника код оформляется блоком с меткой `python`, остальной текст — без Markdown-разметки.

```bash
.venv/bin/python tools/capture_theme_previews.py
```

После изменений проведи одну общую проверку поведения и отображения на обычной и узкой ширине.

## Цифровая подпись изменений и релизов

- По просьбе владельца создавай новые коммиты и теги релизов с цифровой подписью.
- Используй настроенный ключ владельца, связанный с его учётной записью GitHub. Не создавай и не загружай новый ключ без разрешения.
- После отправки проверяй, что GitHub подтверждает подпись (Verified).
- Если подходящий ключ недоступен, сообщи об этом до публикации. Не заменяй подписанный коммит или тег неподписанным без согласования.
- Не переписывай опубликованную историю и не заменяй существующие теги только ради отметки Verified без отдельного указания владельца.
- Подпись коммитов и тегов не заменяет подпись Windows-установщика и проверку работоспособности приложения.
